# Vibe coding 工作流

这套文档的作用：**你用中文说需求，它变成可执行的代码**，中途不靠我猜。

---

## 一、文件地图

| 文件 | 是什么 | 谁改 |
|---|---|---|
| `AGENTS.md` | 项目约定（怎么跑、写什么语言、改哪些目录） | 定下来就不常动 |
| **`.scratch/gacha-simulator/spec.md`** | **需求唯一权威**。做什么、不做什么、为什么 | 你说我写 |
| `.scratch/gacha-simulator/issues/NN-*.md` | 从 spec 拆出的任务单，一张单一次改动 | 我拆，你审 |
| `GLOSSARY.md` | 术语表。同一个词只能有一种意思 | 出现新词就加 |
| `docs/reference/` | 参考实现的事实拆解。**不是需求**，只是底料 | 只读 |
| `docs/agents/` | 工程技能的配置（issue 放哪、标签叫什么） | 已定 |

判断标准很简单：**spec 里没写的功能就不做**，哪怕它看起来很明显。

## 二、五步循环

```
① 你说需求（口语，不用管格式）
        ↓
② 我写进 spec.md：问题 → 方案 → 用户故事 → 实现决策 → 测试决策 → 范围外
        ↓
③ 拆任务单：一个任务单 = 一次可独立验收的改动，写进 issues/
        ↓
④ 实现一个任务单 → 跑起来验 → 中文提交
        ↓
⑤ 你验收，不满意就回①，改 spec 再改代码
```

### ① 提需求怎么提才不容易跑偏

有用的信息是这四样，缺了我会问：

- **谁用**：群里所有人 / 只有管理员 / 只有某个人
- **在什么场景下用**：聊天里打指令 / 自然语言说「帮我十连」
- **看得到什么结果**：一段文字 / 一张图 / 两者都有
- **什么算不对**：比如「概率不能明显偏离官方」「不能刷次数」

不用一次说全。先说要什么，我把不清楚的列成 spec 里的待定项再回来问。

### ② spec 长什么样

固定六段（源自 `/to-spec` 技能），每段都是人话：

- **问题陈述** —— 用户视角的痛点
- **解决方案** —— 用户视角的解法
- **用户故事** —— `作为<角色>，我想要<功能>，以便<收益>`，尽可能穷尽
- **实现决策** —— 用什么结构、存什么、接口长什么样（不写文件路径，会过时）
- **测试决策** —— 什么算好测试（只测外部行为）
- **范围外** —— 明确不做的，防止以后扯皮

### ③ 任务单的粒度

一条任务单要满足：**能单独提交、能单独验收、失败能回滚**。

反例：「实现抽卡功能」——太大，验收不了。
正例：「单抽命令按官方权重出结果，输出文字，不扣次数（先不接数据库）」。

## 三、三种常见说法 → 三种动作

| 你说 | 我做 |
|---|---|
| 「再加个功能」 | 先补 spec（用户故事 + 范围外），再拆任务单 |
| 「这个行为不对」 | 先确认是 spec 写错了还是代码写错了；spec 错就改 spec |
| 「崩了 / 报错」 | 诊断循环：先复现，定位到具体模块，再改 |

**任何情况下 spec 先行。** 代码和 spec 打架时，以 spec 为准；如果 spec 本身不合理，
先改 spec 再说 —— 不能默默让代码变成事实。

## 四、我的硬规则

1. **遇到分叉先问你**，两条路都说得通时不替你选。
2. **一个模块一次提交**，提交信息中文 + `feat:`/`fix:`/`docs:` 前缀。
3. **只改本仓库和 `data/plugin_data/astrbot_plugin_game_gacha/`**，AstrBot 源码不动。
4. **术语照 `GLOSSARY.md` 用**。你说「水位」我不会写成「保底计数器」再混用。
5. **不确定就写进 spec 的待定项**，不在代码里偷偷发明行为。
