# Spec: 抽卡模拟器（明日方舟）

> Parent PRD: docs/features/gacha-simulator/PRD.md
> Related ADR: None（本文件已记录分层与数据源两项决策的理由）
> 状态：可执行（2026-11-15），可直接拆 issue
> 规则依据：PRTS「寻访规则」与「将雪投火」卡池公告原文 + 官方 `gacha_table.json` 实测

## Overview

一个 AstrBot 插件，在群聊里模拟《明日方舟》寻访：每日签到领抽数，用 `/单抽`、`/十连`
在**真实卡池**里抽，结果出图，并记录潜能、六星水位、选调进度、寻访数据契约。

三条贯穿全篇的结构性约束：

1. **core 与游戏无关，方舟的一切沉在 `games/arknights/`。** 本期不定义游戏接口 Protocol，
   只为星铁预留目录与「权重函数 / 计数推进 / 保证规则」三段式形状。
2. **数据双源，各管一半。** 官方 `gacha_table.json` 只提供骨架（池 id、规则类型、起止时间、
   保底参数、限定赠送参数）；**池名与 UP 名单来自 PRTS「卡池一览」**——官方表对近期池只给
   占位名与空详情，这一条是本 Spec 对 PRD 数据决策的更正，理由见 `### Business Rules / R-14`。
3. **一次抽卡是一个事务。** 扣抽数、出结果、推计数器、写存档要么全成要么全不成；渲染在事务
   之外，渲染失败不得回滚已入账的结果。

## Functional Specification

### State Transitions

**单次抽取（一次 pull 的完整链路）**

```
解析参数 → 定池 → 校验余额 → [事务开始]
   ├─ 计算 6★ 概率（按水位）
   ├─ 判定星级
   ├─ 若 6★：检查保证规则（定向选调 / 选调 / 联动 120）→ 命中则锁定目标干员
   ├─ 星级内按权重选干员
   ├─ 推进计数：六星水位、选调累计、定向选调累计、联动计数、契约、井计数、池内前10抽
   ├─ 扣抽数 + 写潜能 + 写计数
[事务提交] → 渲染（失败则降级文字）→ 发送
```

十连 = 同一事务内连做 10 次上述循环；**任何一次的前置不成立都不允许「已抽一半」**。

**卡池状态**（由起止时间派生，不落库）

```
upcoming ──(now ≥ open)──→ active ──(now ≥ end)──→ ended
```

- `active`：可抽、可查、可兑换
- `ended`：仅可查（UP 名单与时间），抽卡入口拒绝，兑换请求按 R-09 拒绝
- 池进入 `ended` 时触发一次惰性结算（契约折算 / 选调计数清零 / 水位分组清零），
  在用户下一次与该池相关的请求里补做，不依赖定时任务

**水位分组生命周期**

| 分组 | 何时清零 |
|---|---|
| `standard` | 只在**出 6★** 时归零，永不过期 |
| `classic` | 只在出 6★ 时归零，永不过期 |
| `limited:<pool_id>` | 池结束时整组删除 |
| `linkage:<pool_id>` | 池结束时整组删除 |
| `backflow:<pool_id>` | 池结束时整组删除 |

### Business Rules

**R-01 基础概率**（PRTS 原文）：6★ 2.00%、5★ 8.00%、4★ 50.00%、3★ 40.00%。

**R-02 六星概率递增**：设 `c` = 本抽之前连续未出 6★ 的次数。

```
p6 = min(1.0, 0.02 + 0.02 × max(0, c − 49))
```

即第 1–50 抽恒为 2%，第 51 抽 4%，此后每抽 +2%，第 99 抽达 100%（硬保底）。
其余星级按 8 : 50 : 40 等比占用剩余概率 `1 − p6`。

**R-03 新池前 10 抽保底**：每个池、每个用户，前 10 抽内必出 5★ 以上，每池限一次。
第 10 抽仍无 5★ 以上时，该抽强制至少 5★（先按 6★ 概率判定，未中则落 5★）。
计数按「池」而非「池型」，官方字段 `guarantee5Avail`/`guarantee5Count` 为真源，缺省 10。

**R-04 水位分组**（PRTS 原文逐条对应）

| 官方说法 | 分组 |
|---|---|
| 标准寻访之间继承，不因寻访结束清零 | `standard`：`NORMAL` `SINGLE` `DOUBLE` `SPECIAL` `ATTAIN` |
| 中坚寻访「仅对中坚寻访范围生效」 | `classic`：`CLASSIC` `CLASSIC_DOUBLE` `CLASSIC_ATTAIN` |
| 限定寻访之间**不**累计，结束清零 | `limited:<pool_id>` |
| 联动寻访不累计，结束清零 | `linkage:<pool_id>` |
| 跨年欢庆（中坚）不累计，结束清零 | `fes:<pool_id>`（`FESCLASSIC`，不复用 `classic`） |
| 归航寻访不累计，结束清零 | `backflow:<pool_id>` |
| 新年特别十连不与标准寻访互通 | `specified:<pool_id>`（`GACHAWITHSPECIFIED6`） |

分组关系写进 `resources/pity_groups.json`，不硬编码在代码里。

**R-05 常驻选调**（`NORMAL` 常驻轮换、`CLASSIC`、`CLASSIC_DOUBLE`）：
本期累计 150 抽后，下一次 6★ 必为当期 UP 6★ **之一**；累计 300 抽后，下一次 6★ 必为
**另一名** UP 6★。两个条件各只生效一次，本期结束清零，不跨期累计。
触发时结果里标注「选调」。

**R-06 限时定向选调**（`SINGLE`，单 6★ UP 的活动池）：
**连续** 150 抽未获得该池 UP 6★ → 下一次 6★ 必为该 UP 6★，本期仅一次。
「连续」意味着提前抽到 UP 时计数清零且**不视为选调已生效**——这是 PRTS 明确点出的区别。

**R-07 限定池 300 井**：本期累计 300 抽时，**额外赠送**当期限定 6★（每期限一次）。
该次赠送不产契约、不推进也不重置水位（与「又抽到一个」不同）。计数仅绑定本池，结束清零。

**R-08 寻访数据契约**：限定池每抽 +1，十连 +10。池结束（兑换所关闭）时按 **1 张 = 6 张
寻访参数模型** 折算为永久余额；参数模型本期**只记录与展示，不做交换所**。
配置 `contract_expire_mode` 可切 `clear`（直接清零），默认 `convert`。

**R-09 契约兑换三档**（仅限进行中的限定池）

| 档位 | 目标 | 目标来源 |
|---|---|---|
| 75 | 当期 5★ UP | 该池 UP 名单里的 5★ |
| 200 | 解限满 3 年的旧限定 6★（春节系列为 4 年） | 派生表 `limits.json`，见 R-14 |
| 300 | 本期可兑换的 6★（当期 UP 两名 + 往期同类限定） | 本期 UP 名单；往期同类不在本期名单时，仅接受名单内目标 |

用户未指定目标时：75 档唯一直接兑换；200/300 档列出候选要求补名字。池已结束一律拒绝。

**R-10 联动寻访**：
- 池开池时间 ≥ 2026-05-01（迭代 1）：每 120 抽必得联动 6★，提前抽到则计数清零
- 池开池时间 < 2026-05-01（迭代 0）：前 120 抽必得联动 6★，仅一次
- 迭代 1 另有 5★ 选调：前 50 抽未出 UP 5★ → 下一次 5★ 必为 UP 5★
- 120 阈值取官方 `linkageParam.guaranteeTarget6Count`，缺省 120

**R-11 限定池权重分配**：UP 6★ 合计占 6★ 的 **70%**（两名各 35%，单人 UP 则独占 70%）；
剩余 30% 由池内其他 6★ 分配，其中**同类系列最近登场的三名限定干员权重 ×5**。
不同池型的 UP 占比写进 `resources/pool_rules.json`（`up6_share` / `up5_share`）：

| 池型 | up6_share | up5_share | 说明 |
|---|---|---|---|
| NORMAL / CLASSIC / CLASSIC_DOUBLE | 0.5 | 0.5 | 两名 6★ 各 25% |
| SINGLE | 0.5 | 0.5 | 单 6★ 独占 50% |
| LIMITED | 0.7 | 0.5 | 原文「占 6★ 出率的 70%」 |
| LINKAGE | 0.5 | 0.5 | |
| DOUBLE / SPECIAL / BACKFLOW | 1.0 | 1.0 | 池内 6★ 有且仅有名单内几人 |

**R-12 池指定与消歧**：`/单抽 [类别] [池名前缀]`，类别取 `限定|常驻|限时|中坚|联动`。

| 输入 | 行为 |
|---|---|
| 无参数 | 优先当期限定池；无则取**结束时间最晚**的进行中池 |
| 只有类别 | 该类仅 1 个进行中池 → 抽它；≥2 → 列出候选并中止 |
| 类别 + 前缀 | 在该类内按池名前缀匹配；唯一 → 抽；多义 → 列出候选并中止 |
| 只有前缀（首字不像类别） | 全池范围前缀匹配，规则同上 |
| 纯数字 | 不匹配任何池，回「本插件不使用编号，请用池名」 |

前缀匹配：去空白后 `池名.startswith(前缀)`；命中 0 个时降级为包含匹配，仍 0 个则报错。

**R-13 抽数扣除**：单抽扣 1、十连扣 10，余额不足则整单拒绝，不产生任何结果。
同一用户并发请求用**每用户锁**串行化，避免重复扣减。

**R-14 数据双源与降级**（对 PRD 决策的更正，见 `Open Questions`）

| 字段 | 来源 | 实测依据 |
|---|---|---|
| 池 id / 规则类型 / 起止时间 / 保底参数 / 井参数 / 联动阈值 | 官方 `gacha_table.json` | 460 池全有 |
| 池名 / UP 6★ / UP 5★ / UP 4★ | PRTS「卡池一览」 | 官方表近期池名是占位串「适合多种场合的强力干员」，`gachaPoolDetail` 为空或 `-` |
| 限定干员系列与解限时间（供 200 档） | 由前两者派生 | `limitParam.limitedCharId` + 池结束时间 |

官方表实测缺口：近 400 天 86 个池里，62 个池名是占位串；`SINGLE`/`DOUBLE`/`NORMAL` 的
`gachaPoolDetail` 全为 `-`（1 字节），`dynMeta` 只对 `CLASSIC`/`SPECIAL`/`ATTAIN`/`BACKFLOW`/
`FESCLASSIC`/`CLASSIC_DOUBLE`/`GACHAWITHSPECIFIED6` 有值。**因此官方表不能单独产出 UP 名单。**

对齐键 = 起止时间（官方是 unix 秒，PRTS 转 UTC+8 后取秒，精确相等）；对齐失败时用池名二次匹配。

降级链：

1. PRTS 抓取成功 → 用最新骨架 + 最新名单
2. PRTS 失败 → 用内置快照的名单，池骨架仍取官方最新
3. 两源都失败 → 全量用内置快照，并在 `/卡池查询` 顶部标注「数据为 X 前的快照」
4. 名单缺失且骨架有该池 → 该池按「无 UP 加成」运行（全池均分），结果标注
   「UP 名单未获取」；**不允许**因缺名单就整池不可用

**R-15 交易与渲染顺序**：抽卡事务先提交，再渲染。渲染抛异常 → 发文字结果 + 记警告日志，
抽数与计数器保持已入账状态。

**R-16 用户隔离**：所有存档以 `(平台, 用户 id)` 为主键维度，群内互不可见；管理员操作同样写
被操作者的行，不合并。

### Error Scenarios

| 场景 | 用户看到 | 副作用 |
|---|---|---|
| 抽数不足 | 「需要 10 抽，你还有 3 抽」 | 无 |
| 无进行中的池 | 「当前没有进行中的卡池，数据可能未更新」 | 无 |
| 类别下有多个池 | 候选列表 + 「请补池名前几个字」 | 无 |
| 前缀匹配 0 个 | 「没有名称含「XXX」的进行中卡池」+ 当前池名列表 | 无 |
| 池已结束 | 「该卡池已于 X 结束，不能抽取」 | 无 |
| 当天已签到 | 「今天已经领过了」 | 无 |
| 非管理员调用改次数 | 「这条只能管理员用」 | 无 |
| 契约不足 | 「需要 75 张，你有 30 张」 | 无 |
| 兑换目标不在名单 | 列出可兑换目标 | 无 |
| 兑换已结束池 | 「该卡池的交换所已关闭」 | 无 |
| 数据未就绪（首次启动且无快照） | 「数据初始化中，请稍后再试」 | 只读指令仍可用 |

## Technical Specification

### Data Model

**SQLite**（`data/plugin_data/astrbot_plugin_game_gacha/gacha.db`）

| 表 | 字段 | 说明 |
|---|---|---|
| `users` | `uid` PK, `platform`, `tickets`, `created_at`, `last_signin` | 抽数余额与签到日（`YYYY-MM-DD`，本地时区） |
| `inventory` | `uid`, `char_id`, `count`, `first_at`，PK(`uid`,`char_id`) | `count` 为累计获得次数，潜能 = `count − 1`（上限 5） |
| `pity` | `uid`, `group_key`, `six_counter`，PK(`uid`,`group_key`) | `six_counter` = 连续未出 6★ 次数 |
| `pool_state` | `uid`, `pool_id`, `pulls`, `first10_hit`，PK(`uid`,`pool_id`) | 池内累计抽数与「前 10 抽保底是否已用」 |
| `pool_select` | `uid`, `pool_id`, `up_miss_counter`, `select150_used`, `select300_used`, `target6_locked` | `up_miss_counter` 供 R-06；`target6_locked` 供 R-05 第二名 |
| `limited_state` | `uid`, `pool_id`, `contracts`, `well_claimed`, `linkage_counter`, `up5_miss_counter` | 限定/联动专有计数 |
| `params` | `uid`, `amount` | 寻访参数模型余额（只增不减，本期无交换所） |
| `meta` | `key`, `value` | 数据版本（官方表 ETag、PRTS 快照时间） |

**数据文件**（随包，`resources/snapshot/`）

| 文件 | 内容 | 生成方式 |
|---|---|---|
| `gacha_table.json` | 官方表裁剪：只保留池骨架需要的字段 | `tools/build_data.py` |
| `banners.json` | PRTS 卡池一览：池名、起止、UP 6★/5★/4★、小节名 | 同上 |
| `limits.json` | 限定干员派生表：`char_id` → 系列（春节/庆典/夏季）、首次登场池结束时间、200 档可用日期 | 同上 |
| `pool_rules.json` | 池型 → `up6_share`/`up5_share`/选调类型/井阈值 | 手写，随规则变化更新 |
| `pity_groups.json` | 池型 → 水位分组 | 手写 |

**运行时缓存**（`plugin_data/.../cache/`）：官方表与 PRTS 页面的 ETag / 最后抓取时间。

| `games/arknights/views.py` | 文字结果格式 | |

### Validation Rules

- 抽数余额：单抽 ≥1、十连 ≥10，否则整单拒绝
- 池名：去首尾空白，最长 20 字；不接受纯数字
- 类别字符串只认五个词，其余当作池名前缀处理
- 改次数：绝对值 ≤ 100000，负数不得使余额为负（负数超额时按「清零」处理并回报实际改动量）
- 契约兑换：档位只认 75/200/300，目标必须在该档候选名单内
- 日期：签到按本地时区自然日判定，跨日以 `YYYY-MM-DD` 不等为准
- 数值落库前全部转 int，概率计算保留 double，不落库

### Known Non-Testable Acceptance Criteria

PRD 里的两个视觉缺陷**没有可验证基准**（用户选择「验收时再提」）。因此本 Spec 只把可判定的
部分写成规则，其余明确标为不可测：

| 缺陷 | 本 Spec 能测的部分 | 不可测部分 |
|---|---|---|
| 十连立绘偏大 | 立绘矩形不超出卡片边界、不与姓名条重叠（几何断言，可自动化） | 「看起来比游戏里大一圈」 |
| 单抽字体不一致 | 中文无缺字（字体覆盖全部用字，可断言）、字号在卡片内不溢出 | 「与游戏内字体一致」 |

不做像素级对齐；若日后要真修，需先补游戏截图作为基准（PRD `Further Notes` 已记）。

2. **「卫戍」是哪类池**：官方 13 个 `gachaRuleType` 里没有这个类型，怀疑是某个池的具体名字。
   在明确之前，它按名称前缀匹配处理，不单独建类。
3. **`DOUBLE`（联合行动）有无 150 定向选调**：PRTS 只写了常驻选调与限时单 UP 定向选调；联合
   行动是「4 名 6★ 有且仅有」的全池，本 Spec 按「无选调、4 名均分」处理。若实机有保底，需
   补一条规则。
4. **契约到期**：官方是折算成参数模型（1:6，永久），PRD 原写「清零」——那是基于我说错的
   前提。本 Spec 默认折算但只记录余额、不做参数模型交换所，并留 `contract_expire_mode=clear`
   开关。要真清零还是真折算，你定。
5. **200 档的系列判定精度**：系列（春节/庆典/夏季）由限定池开池月份推断（1–2 月春节、8 月
   夏季、其余庆典），若有错判会让个别干员的 200 档提前或延后一期。需要更高精度就得引入
   公告文本解析。
6. **`/契约兑换` 是第 7 条指令**，PRD 功能清单没列。它必须有，否则 R-09 的兑换无法触发。
