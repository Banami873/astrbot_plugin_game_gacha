## Overview

一个 AstrBot 插件，在群聊里模拟《明日方舟》寻访：每日签到领抽数，用 `/单抽`、`/十连`
在**真实卡池**里抽，结果出图，并记录潜能、六星水位、选调进度、寻访数据契约。

三条贯穿全篇的结构性约束：

1. **core 与游戏无关，方舟的一切沉在 `games/arknights/`。** 本期不定义游戏接口 Protocol，
   只为星铁预留目录与「权重函数 / 计数推进 / 保证规则」三段式形状。
2. **数据双源，各管一半。** 官方 `gacha_table.json` 只提供骨架（池 id、规则类型、起止时间、
   保底参数、限定赠送参数）；**池名与 UP 名单来自 PRTS「卡池一览」**——官方表对近期池只给
   占位名与空详情，这一条是本 Spec 对 PRD 数据决策的更正，理由见 `### Business Rules / R-14`。
3. **一次抽卡是一个事务。** 扣抽数、出结果、推计数器、写存档要么全成要么全不成；渲染在事务
   之外，渲染失败不得回滚已入账的结果。

## Functional Specification

### State Transitions

**单次抽取（一次 pull 的完整链路）**

```
解析参数 → 定池 → 校验余额 → [事务开始]
   ├─ 计算 6★ 概率（按水位）
   ├─ 判定星级
   ├─ 若 6★：检查保证规则（定向选调 / 选调 / 联动 120）→ 命中则锁定目标干员
   ├─ 星级内按权重选干员
   ├─ 推进计数：六星水位、选调累计、定向选调累计、联动计数、契约、井计数、池内前10抽
   ├─ 扣抽数 + 写潜能 + 写计数
[事务提交] → 渲染（失败则降级文字）→ 发送
```

十连 = 同一事务内连做 10 次上述循环；**任何一次的前置不成立都不允许「已抽一半」**。

**卡池状态**（由起止时间派生，不落库）

```
upcoming ──(now ≥ open)──→ active ──(now ≥ end)──→ ended
```

- `active`：可抽、可查、可兑换
- `ended`：仅可查（UP 名单与时间），抽卡入口拒绝，兑换请求按 R-09 拒绝
- 池进入 `ended` 时触发一次惰性结算（契约折算 / 选调计数清零 / 水位分组清零），
  在用户下一次与该池相关的请求里补做，不依赖定时任务

**水位分组生命周期**

| 分组 | 何时清零 |
|---|---|
| `standard` | 只在**出 6★** 时归零，永不过期 |
| `classic` | 只在出 6★ 时归零，永不过期 |
| `limited:<pool_id>` | 池结束时整组删除 |
| `linkage:<pool_id>` | 池结束时整组删除 |
| `backflow:<pool_id>` | 池结束时整组删除 |

### Business Rules

**R-01 基础概率**（PRTS 原文）：6★ 2.00%、5★ 8.00%、4★ 50.00%、3★ 40.00%。

**R-02 六星概率递增**：设 `c` = 本抽之前连续未出 6★ 的次数。

```
p6 = min(1.0, 0.02 + 0.02 × max(0, c − 49))
```

即第 1–50 抽恒为 2%，第 51 抽 4%，此后每抽 +2%，第 99 抽达 100%（硬保底）。
其余星级按 8 : 50 : 40 等比占用剩余概率 `1 − p6`。

**R-03 新池前 10 抽保底**：每个池、每个用户，前 10 抽内必出 5★ 以上，每池限一次。
第 10 抽仍无 5★ 以上时，该抽强制至少 5★（先按 6★ 概率判定，未中则落 5★）。
计数按「池」而非「池型」，官方字段 `guarantee5Avail`/`guarantee5Count` 为真源，缺省 10。

落地口径（用户 2026-11-15 明确）：**只有每个池的第一个十连受保护**，前 10 抽内出过一次
5★ 以上即视为达成，之后第 2、第 3 个十连完全按概率走——整批全 3★ 也不兜底。「前 10 抽」
按**池内累计抽数**算，不按批次：先单抽 5 次再十连，保底仍落在累计第 10 抽。

**R-04 水位分组**（PRTS 原文逐条对应）

| 官方说法 | 分组 |
|---|---|
| 标准寻访之间继承，不因寻访结束清零 | `standard`：`NORMAL` `SINGLE` `DOUBLE` `SPECIAL` `ATTAIN` `GACHAWITHSPECIFIED6` |
| 中坚寻访「仅对中坚寻访范围生效」 | `classic`：`CLASSIC` `CLASSIC_DOUBLE` `CLASSIC_ATTAIN` |
| 限定寻访之间**不**累计，结束清零 | `limited:<pool_id>` |
| 联动寻访不累计，结束清零 | `linkage:<pool_id>` |
| 跨年欢庆（中坚）不累计，结束清零 | `fes:<pool_id>`（`FESCLASSIC`，不复用 `classic`） |

分组关系写进 `resources/pity_groups.json`，不硬编码在代码里。

`GACHAWITHSPECIFIED6`（卫戍寻访）进 `standard` 组的两条依据：官方公告明写「本次活动【卫戍寻访】
为【标准寻访】」；其 `gachaPoolId` 前缀为 `NORM_`，是官方自己的分类。全部 460 池中该类型
只有 1 个实例（`NORM_79_0_3`，2026-11-08 16:00 ~ 2026-12-02 03:59），没有历史包袱。

**R-05 常驻选调**（`DOUBLE` 常驻标准寻访、`CLASSIC`、`CLASSIC_DOUBLE`）：
本期累计 150 抽后，下一次 6★ 必为当期 UP 6★ **之一**；累计 300 抽后，下一次 6★ 必为
**另一名** UP 6★。两个条件各只生效一次，本期结束清零，不跨期累计。
触发时结果里标注「选调」。

落地口径（2026-11-18，实现 issue 06 时定死，`tests/test_select.py` 逐条钉住）：

- **判定时点是「之后」**：出 6★ 时看本池累计抽数（`pool_state.pulls`，不含本抽）。只有
  `pulls ≥ 阈值` 才触发——第 150 抽本身出 6★ 不算，官方原文是「累计寻访 150 次**后**，
  下一次获得的 6 星干员」。差这一抽会让选调整体提前一次。
- **一抽最多触发一档**，150 档先判、300 档后判。正常存档里 300 档不可能越过 150 档：硬保底
  99 抽，150 之后到 300 之间必然出过 6★。
- **150 档在 UP 名单内随机一名**（官方不指定是谁），选中的记进 `target6_locked`；300 档只在
  UP 名单 ≥2 人时可用，且排除已锁定的那一名。**只有一名 UP 时不触发 300 档，也不置位**——
  这一档永远等不到「另一名」，置位只会让以后真有两名 UP 的池误以为已经用过。
- **选调只改「6★ 里是谁」，不改 6★ 出率**：这一抽仍按水位判星级，命中的 6★ 直接落锁定目标，
  不再走 UP 份额那套权重；水位照常归零、照常入仓库。常驻/中坚池不产契约，与井无关。
- **UP 名单缺失时整条规则不启用**（`banners.json` 没有这个池）：锁不到人就不能假装锁了，
  文案也不标注。这是 R-14 降级链的同一取舍——少一个机制好过报错或锁错人。
- **换期靠 `pool_id` 天然隔离**：`pool_select` 一行对应一个池，新池从零开始；不清表也不会
  串期，因为官方池 id 不复用。清表只是省空间，不是正确性要求。
- 选调状态与抽数、水位、仓库在**同一个事务**里落库（R-15 的事务顺序不变）。

**R-06 限时定向选调**（`SINGLE`，单 6★ UP 的活动池）：
**连续** 150 抽未获得该池 UP 6★ → 下一次 6★ 必为该 UP 6★，本期仅一次。
「连续」意味着提前抽到 UP 时计数清零且**不视为选调已生效**——这是 PRTS 明确点出的区别。

计数口径（2026-11-18 拆 issue 14 时定死）：`up_miss_counter` **数抽数，不数六星**。每抽 +1，
抽到本池 UP 6★ 才归零；中途歪出别的 6★ 不清零（官方原文是「进行 150 次寻访后仍未获得当期
6 星干员」，连续的是**寻访次数**，不是「歪的次数」）。把它写成「每歪一次六星 +1」会让保底
晚来几十抽，而且抽起来看着还挺像。

落地口径（2026-11-18，实现 issue 14 时定死，`tests/test_select.py` 的
`TestConsecutiveBook` / `TestDrawBatchConsecutive` / `TestConsecutiveStore` 逐条钉住）：

- **计数在每抽末尾推进，不看星级**：每抽结束就更新 `up_miss_counter`——抽到本池 UP 6★ 归零，
  其余（含歪出来的其他 6★）一律 +1。写成「只在没出 6★ 时 +1」会让计数永远追不上 150。
- **判定时点与 R-05 同构**：摇出 6★ 时看**本抽之前**的计数，`≥ 150` 才锁。第 150 抽本身出 6★
  时计数是 149，不触发；第 151 抽起才满足「150 次寻访后仍未获得」。
- **`select150_used` 与 R-05 共用**：一个池要么登记在 `select_by_rule_type`（累计口径），要么
  登记在 `consecutive_select_by_rule_type`（连续口径），不会同时适用，所以「第一档已用」
  只占一列。两个表**分开是刻意的**——同一份配置里混着两种口径，读的时候还得再查一次
  「这是哪种」，迟早写错。
- **中途自然抽到 UP 只清零计数、不置位**：这是「连续」与「累计」唯一的区别，也是最容易写反
  的地方。置位就等于「歪一百抽后抽到 UP 也算选调用过」，之后再也攒不出第二次。
- **UP 名单缺失时整条规则不启用**（与 R-05 同一取舍）：连「谁是 UP」都不知道就没法计数，
  于是计数保持 0、不锁人、不标注。
- **换期靠 `pool_id` 隔离**：新池的 `up_miss_counter` 从 0 开始，旧池那一行不参与判定。

**R-06b 无选调的名单池**：`GACHAWITHSPECIFIED6`（卫戍）、`NORMAL`（联合行动）、`SPECIAL`
（定向甄选）三类**都没有选调**（用户 2026-11-15 确认）。这三类的 6★ 是「池内仅有名单内
几人」，不存在「累计/连续 150 抽必得其中某一名」的机制。实现上不为它们写 `up_miss_counter`
的判定分支，抽到谁全按均分权重走。

**R-07 限定池 300 井**：本期累计 300 抽时，**额外赠送**当期限定 6★（每期限一次）。
该次赠送不产契约、不推进也不重置水位（与「又抽到一个」不同）。计数仅绑定本池，结束清零。

落地口径（2026-11-18，实现 issue 07 时定死）：

- **判定时点**：本批跨越 300 的那一次，条件是 `pulls_before < 300 <= pulls_after`。十连从
  295 抽到 305 也算触发；不从「第 300 抽那一刻」判，否则十连跨过 300 时会漏掉。
- **赠送对象**：`limitParam.limitedCharId`（官方自己写的「这一期的限定是谁」）。缺失时退到
  UP 6★ 名单第一名；两者都没有时不赠送、**也不置位**——数据补齐之后下一批还能补上。
  这比「抽不到就当送过」安全。
- **走仓库不走结果**：赠送单独入 `inventory`，**不**并进这一批的抽卡结果。抽卡事务要求
  「结果条数 == 扣的抽数」，把礼物塞进去会让校验把整批拒掉。文案单独一行说明。
- **阈值来自配置**：`pool_rules.json` 的 `well_by_rule_type`（`{"LIMITED": 300}`），
  未登记的池型即无井。与选调同一取舍：数据驱动，代码里不出现池型字面量。

**R-08 寻访数据契约**：限定池每抽 +1，十连 +10。池结束（兑换所关闭）时**剩余契约直接作废**，
不折算为寻访参数模型——**这是本项目对官方的刻意简化**（官方按 1:6 折算成永久参数模型，
但参数模型交换所不在本期范围，留着余额只会变成永远无法使用的数字）。
结果页在池剩余 ≤3 天时提示「契约将于 X 失效」。

落地口径（2026-11-18，实现 issue 07 时定死）：

- **产出速率来自配置**：`pool_rules.json` 的 `contracts_by_rule_type`（`{"LIMITED": 1}`），
  值表示「每抽几份」。未登记的池型即不产契约，联动池也不产（官方只在限定寻访里给契约）。
- **作废靠惰性结算**：不做定时任务。用户下次抽卡时，若他名下有已结束池的
  `limited_state` 行，整行删掉——池结束后池 id 不再可抽，删行等价于「剩余契约归零」，
  同时省掉一次全表扫描。清理失败只告警，不挡这次抽卡（与过期水位的处理一致）。
- **显示**：限定池每批结果带一行「寻访数据契约 N 份」；池剩余 ≤3 天时追加失效时刻
  （形如「本池剩余 2 天 5 小时，契约将于 12-02 12:00 失效」）。出图成功时这句进简报，
  因为图上不画契约。

**R-09 契约兑换三档**（仅限进行中的限定池）

| 档位 | 目标 | 目标来源 |
|---|---|---|
| 75 | 当期 5★ UP | 该池 UP 名单里的 5★ |
| 200 | 解限满 3 年的旧限定 6★（春节系列为 4 年） | 显式表 `limits.json`（不靠公式推导，见下） |
| 300 | 本期可兑换的 6★（当期 UP 两名 + 往期同类限定） | 本期 UP 名单；往期同类不在本期名单时，仅接受名单内目标 |

用户未指定目标时：75 档唯一直接兑换；200/300 档列出候选要求补名字。池已结束一律拒绝。

**两档的分界（官方公告实测，2026-11-15）**：同一期交换所里，300 档列的是「当期 UP 两名 +
已解限但未到年限的往期限定」，200 档列的是「已过年限的往期限定」。以
[【承诺】](https://ak.hypergryph.com/news/2825)（2026-05-01 庆典）为例：

- 300 档 8 名：当期 2 名 + 新约能天使 / 荒芜拉普兰德 / 维什戴尔 / 塑心 / 缪尔赛思 / 缄默德克萨斯
- 200 档 5 名：归溟幽灵鲨 / 耀骑士临光 / 浊心斯卡蒂 / 迷迭香 / W
- 上一期庆典的凛冬异格（2025-11）**两档都没出现**——登场不满一年时尚未「解限」

即「解限」= 登场满一年后进入交换所，「解限满 3 年（春节 4 年）」表面等于「登场满 4 年
（春节 5 年）」。**但两组边界互相矛盾，不能简化成公式**：

| 干员 | 登场 | 参照池 | 距今 | 实际档位 |
|---|---|---|---|---|
| 百炼嘉维尔 | 2022-08-11 | 2026-08-01 夏季 | 3 年 11 月 21 天（**不满 4 年**） | 200 |
| 缄默德克萨斯 | 2022-11-01 | 2026-05-01 庆典 | 3 年 6 月 | 300 |

同为「不满 4 年」，一个已降档一个没有——说明官方是**逐期逐个点名**，不存在统一偏移量。
故 `limits.json` 用**显式表**：能从公告确认的写精确日期，确认不了的按「庆典 +4 年、夏季 +4 年、
春节 +5 年」近似填充并标 `estimated: true`，兑换界面在估算项上标「按估算日期」。

系列只有三个（官方公告标题即系列名）：**春节**（1–2 月开池）、**夏季**（8 月）、**庆典**
（5 月周年与 11 月感谢庆典同属庆典）。27 个历史限定池按开池月份归类，无一例外。

落地口径（2026-11-19，实现 issue 08 时定死，`tests/test_exchange.py` 逐条钉住）：

- **200 档按系列筛**：交换所只列**本系列**的往期限定。2026-05-01 庆典的 200 档 5 名全是
  庆典系列，同年的夏季 200 档才有百炼嘉维尔；春节的年、夕从未在庆典交换所出现过。所以
  候选 = `limits.json` 里 `series == 本池系列` 且 `discount_from <= now`（同时要求已解限）。
- **300 档排除已降价的人**：同一期里一名干员只出现一次。2026-05-01 庆典的 300 档正好是
  「当期 2 名 + 未降价的往期 6 名」（新约能天使 / 荒芜拉普兰德 / 维什戴尔 / 塑心 /
  缪尔赛思 / 缄默德克萨斯），与 200 档那 5 名零重叠。落地时 300 档候选 = 当期 UP 6★ +
  本池限定范围**减去**已进 200 档者。
- **`limits.json` 由脚本生成**（`tools/build_limits.py`）：先按「庆典 / 夏季 +4 年、春节
  +5 年」估算，再用 `ANNOUNCED` 里能从公告逐字核对的观测点修正——公告列进 200 档的往前
  拉到公告日（百炼嘉维尔 3 年 11 月即降档就是这么来的），仍留在 300 档的推到公告日之后。
  被点名过的条目 `estimated: false`，其余为 `true`，兑换界面在后者标「按估算日期」。改了
  快照之后重跑一次；`--check` 只比对不写盘，`TestLimitsTableIsInSync` 挡住「忘了重跑」。
- **兑换不动水位**：只扣 `limited_state.contracts`、只加 `inventory.count`；不写
  `pool_state` / `pity`，也不产新契约——官方交换所不改变寻访保底。
- **池已结束一律拒绝**：契约随池结束被惰性删行（R-08），所以兑换入口先结算再找池。一个
  进行中的限定池都没有时回「没有进行中的限定寻访」，与「契约不够」用不同的话说。
- **名字解析不猜**：全名优先，其次前缀，最后包含；同一层命中多人（「塔露拉」与「塔露德」
  共享前缀）时把命中的列出来要求补字，不替玩家挑——猜错一次就是几十上百份契约。

**R-10 联动寻访**：
- 池开池时间 ≥ 2026-05-01（迭代 1）：每 120 抽必得联动 6★，提前抽到则计数清零
- 池开池时间 < 2026-05-01（迭代 0）：前 120 抽必得联动 6★，仅一次
- 迭代 1 另有 5★ 选调：前 50 抽未出 UP 5★ → 下一次 5★ 必为 UP 5★
- 120 阈值取官方 `linkageParam.guaranteeTarget6Count`，缺省 120

落地口径（2026-11-18，实现 issue 09 时定死）：

- **迭代看字段，不看日期**：官方 `linkageParam` 自己就分了两代——迭代 1 写
  `{"guaranteeTarget6Char": "char_xxx", "loopTarget6Count": 120}`，迭代 0 只写
  `{"guaranteeTarget6Count": 120}`。9 个联动池实测 6 旧 3 新，与「2026-05-01」分界结论
  完全一致。用字段判定不依赖一个手工维护的日期边界，官方以后再加新池也不会判错。
- **两种口径的判定时点相反，这是本条最容易写错的地方**：
  - 迭代 0 是「**前 N 抽**必得」：本池第 N 抽（`pulls + 1 == N`）若还没获得过联动 6★，
    这一抽强制出 6★ 并落在 UP 名单。用 `linkage_used` 标记「已获得」，只进不退。
  - 迭代 1 是「**每 N 抽**必得」：`linkage_miss` 数「连续多少抽没出 UP 6★」，本抽之前
    已连续 N−1 抽没出时，这一抽强制出 6★ 并锁定 `guaranteeTarget6Char`。抽到目标后
    计数归零，重新攒下一轮，可以反复触发。
  - 与 R-05/R-06 的「150 抽**之后**的下一次 6★」不同：那两条的原文是「进行 150 次寻访后
    仍未获得……则**下一次获得的** 6 星干员必定为」，联动的原文是「每 120 抽必得」，
    没有「下一次获得的」这句话。照抄 150 的时点会让联动保底晚一抽。
- **迭代 1 的 5★ 选调是「池内前 50 抽」口径**，不是连续计数：本池抽数 > 50 且还没获得
  过 UP 5★ 时，下一个 5★ 锁定 UP 5★ 之一。「前 50 抽内自然抽到 UP 5★」同样算达成。
  所以只需一个「是否已获得」的布尔值和 `pool_pulls`，不需要单独的计数器——计数器和
  池内抽数重复，多存一份就多一处能写错。
- **名单缺失即降级**：5★ 名单为空时不做 5★ 选调（锁不到人就不能假装锁了）；联动 UP 6★
  名单为空且池也没有 `guaranteeTarget6Char` 时，6★ 保底同样不启用。
- 联动的 6★ 范围就是 UP 名单 + 标准池，不涉及限定系列，`scope` 不参与。

**R-11 限定池权重分配**：UP 6★ 合计占 6★ 的 **70%**（两名各 35%，单人 UP 则独占 70%）；
剩余 30% 由池内其他 6★ 分配，其中**同类系列最近登场的三名限定干员权重 ×5**。
不同池型的 UP 占比写进 `resources/pool_rules.json` 的 `up_share_by_rule_type`（键是池型，
值 `{"6": …, "5": …}`），没登记的池型落 `default_up_share`：

| 池型 | 6★ 份额 | 5★ 份额 | 说明 |
|---|---|---|---|
| `DOUBLE` / `CLASSIC` / `CLASSIC_DOUBLE` | 0.5 | 0.5 | 常驻与中坚：两名 UP 6★ 各占 25% |
| `SINGLE` | 0.5 | 0.5 | 单 6★ 独占 50% |
| `LIMITED` | 0.7 | 0.5 | 原文「占 6★ 出率的 70%」 |
| `LINKAGE` | 0.5 | 0.5 | |
| `NORMAL` | 1.0 | 1.0 | 联合行动：池内 6★ 只有名单上那 4 人 |
| `SPECIAL` / `FESCLASSIC` | 1.0 | 0.5 | 定向甄选与中坚甄选：6★ 只在可选名单内 |
| `ATTAIN` / `CLASSIC_ATTAIN` | 1.0 | 0.0 | 特选：只列 6★，5★ 走常规 |
| `GACHAWITHSPECIFIED6` | 1.0 | 0.5 | 卫戍：6★ 仅名单内 10 人，均分（各 10%）；5★ 官方公告未列名单，按常规 UP |

**R-11 补充：限定池 6★ 的范围与 5 倍名单**（issue 13，2026-11-15 按 PRTS「寻访规则」原文
核对，四个真实池的官方公告逐字验证）。上面「同类系列最近登场的三名限定 ×5」这句省略了
三条前提，缺一条名单就会算错：

- **6★ 池只有三类人**：当期 UP + **同系列**往期限定 + 标准寻访干员，不是全体 27 名限定。
  系列只三档：春节（开池 1–2 月）、庆典（5 月、11 月）、夏季（8 月），按游戏时间 UTC+8
  判断月份（`11-01 07:00` 在 UTC 下是 `10-31 23:00`，按机器时区会归错系列）。
- **解限期**：限定干员在当期池结束后**最多 11 个月**内不进任何限定寻访。所以「最近三名」
  = 同系列、**已过解限期**、按登场时间倒序的前三名。顺序不能反：先取三名再排除解限期内的，
  只会剩两名。
- **5 倍只落在剩余 30% 内部**（官方原文「获得的 6★ 不是当期出率提升干员的场合」），
  且只作用于 6★，5★ 没有往期加权这回事。当期 UP 自己也在解限期内，必须并回可登场集合。
  公告对「5 倍」的定义是「达到**其他单个 6 星干员**（除当期 UP 外）获得概率的 5 倍」——
  所以基数是剩余 30% 里的**每一个**非 UP 6★（含其他同系列限定），不是只对标准干员加权。

以 2026-05【承诺】为例：庆典系最近登场的是凛御银灰（2025-11）、新约能天使（2025-05）、
荒芜拉普兰德（2024-11），但官方公告的 5 倍名单是**新约能天使 / 荒芜拉普兰德 /
维什戴尔**——凛御银灰登场才 6 个月，未解限，根本不在池子里。四个池的逐字核对见
`issues/13-limited-scope-and-boost.md`。

这些数据全部从骨架快照派生（`games/arknights/limited.py`）：每个 `LIMITED` 池自带
`limitParam.limitedCharId` 与起止时间，**不新增资源文件**。系列判不出来时退化为
「不筛、不加权」——多放几个人只是手感偏差，筛错会直接少一档人。

**R-12 池指定与消歧**：`/单抽 [类别] [池名]`，类别取 `限定|常驻|限时|中坚|联动`。
类别是 `gachaRuleType` 的过滤器，映射写进 `resources/pool_rules.json`：

| 类别 | 包含的 `gachaRuleType` | 搜池时的范围 |
|---|---|---|
| 限定 | `LIMITED` | `LIMITED` + `LINKAGE`（见下） |
| 常驻 | `DOUBLE` | 同左 |
| 限时 | `NORMAL` `SINGLE` `SPECIAL` `ATTAIN` `GACHAWITHSPECIFIED6` | 同左 |
| 中坚 | `CLASSIC` `CLASSIC_DOUBLE` `CLASSIC_ATTAIN` `FESCLASSIC` | 同左 |
| 联动 | `LINKAGE` | 同左 |

**不带任何词只抽限定**：`/十连` = 抽最新的限定池。限定池没开时**报错**（`no_limited`，
文案列出现在开着什么），**不退化**成「最新的池子」——退化的后果是玩家发 `/十连` 抽到
常驻干员，还以为限定开了。要抽别的必须带类别。

**写「限定」时联动也算**：两类都是「限定干员、不进常驻」，玩家嘴里的「限定」通常两者都
指。同时开着时**优先限定**（玩家说限定想的还是当期那个池），只有限定没开才看联动。
`/十连 联动` 则严格只搜联动，没开就报错。

类别之后接池名（前缀优先、无前缀时降级为包含匹配）；类别为空时在全部在开的池里搜。

**`DOUBLE` 与 `NORMAL` 的命名与直觉相反**（issue 05 实测更正）：`DOUBLE` 是**常驻标准寻访**
（双 6★ UP、每 14 天 04:00 轮换），`NORMAL` 是**联合行动**（16:00 开、池内仅 4 名 6★）。
依据是 23 期常驻标准与 6 期联合行动的 PRTS 分节与官方时间逐行一一对应，无一例外；
issue 01 按名字猜反了，本期按 PRTS 分节归类（见 R-14）后才纠正。

`BACKFLOW`（归航寻访）不在表内：它与新人寻访同属**本期不实现**的池型，见下方
「不实现的池型」。

`FESCLASSIC`（跨年欢庆·中坚）归「中坚」——虽然水位不复用 `classic` 组（R-04 给了独立的
`fes:<pool_id>`），但用户认知里它是中坚池，类别归属与水位分组是两件事。
「限时」下会同时开多个池（定向甄选与限时标准实测重叠多次），所以必须靠池名前缀消歧。

**对外池名的三级回落**（2026-11-19 补，用户实测反馈）：池骨架的 `name` 可能是空串——官方
占位串被丢弃，或该期没在 PRTS 对上（常驻标准每期池名是一张图，文字只有序号，实测
`DOUBLE_79_0_5` 就落在这里）。此时**绝不能把内部 id 念给玩家**：`DOUBLE_79_0_5` 既念不出来
也搜不到，看起来像插件坏了。显示顺序为

1. PRTS/官方真名
2. 池型规范名：`DOUBLE` → 常驻标准寻访、`FESCLASSIC` → 中坚甄选、
   `GACHAWITHSPECIFIED6` → 卫戍寻访（只写官方有固定叫法的池型）
3. `「<类别>寻访」`——例如 `SINGLE` 落成「限时寻访」。类别是「其他」时才回落到池 id

只写第 2 条里那三种，是因为其余池型在历史上混用过（`NORMAL` 早期是标准寻访、后期才是
联合行动），写死会把老池标错。第 3 条宁可笼统也不错标。

真名缺官方限定词时补前缀：PRTS 写「甄选15」，游戏里全称是「中坚甄选15」。补的是同义的
官方前缀、不改池名本体，且**匹配同时认原名与显示名**——玩家按公告写法「甄选15」、
按界面写法「中坚甄选15」都必须能选中同一个池。

| 输入 | 行为 |
|---|---|
| 无参数 | 优先当期限定池；无则取**结束时间最晚**的进行中池 |
| 只有类别 | 该类仅 1 个进行中池 → 抽它；≥2 → 列出候选并中止 |
| 类别 + 前缀 | 在该类内按池名前缀匹配；唯一 → 抽；多义 → 列出候选并中止 |
| 只有前缀（首字不像类别） | 全池范围前缀匹配，规则同上 |
| 纯数字 | 不匹配任何池，回「本插件不使用编号，请用池名」 |

前缀匹配：去空白后 `池名.startswith(前缀)`；命中 0 个时降级为包含匹配，仍 0 个则报错。

**R-12b 不实现的池型**：`BACKFLOW`（归航寻访）与新人寻访同属**本期不实现**——
它们面向的是特定状态的玩家（回归 / 新手），不是所有人都能抽的池。

处理方式是在**解析阶段整条丢弃**，不是「列表里藏起来」：`resources/pool_rules.json` 的
`unimplemented_rule_types` 列出要跳过的 `gachaRuleType`，`parse_pools` 见到即丢，
下游任何路径都不会看到它。这样 `/卡池查询`、池名匹配、抽卡入口不必各自记得排除一次。

不可用「按时间判活动」来处理：官方给归航寻访的 `endTime` 是 `1903809599`（2030 年），
占位值会让它永远算作进行中，列出「剩 1262 天」的假池。

配置文件缺失或该段损坏时退回内置默认值 `{"BACKFLOW"}`——漏排除比多排除难看。

**R-13 抽数扣除**：单抽扣 1、十连扣 10，余额不足则整单拒绝，不产生任何结果。
同一用户并发请求用**每用户锁**串行化，避免重复扣减。

**实现口径（issue 05 落地时改了顺序，2026-11-15）**：实际做法是**所有池型的名单都取 PRTS**，
不先读 `dynMeta`。原因是抓一次卡池一览就同时拿到四类池的名单与池名，而按 `dynMeta` 分六种
结构各写一段提取代码，收益只是省一次请求、代价是六段互不相同的解析逻辑与六种失败模式。
本期沿用既有的一处例外：`GACHAWITHSPECIFIED6` 的 `dynMeta.charIdList`（卫戍 10 名 6★）
早在 issue 01/03 就已提上来供抽卡内核使用，PRTS 给出的同一份名单与它一致，两处不冲突。

官方表实测缺口：近 400 天 86 个池里，62 个池名是占位串；`SINGLE`/`DOUBLE`/`NORMAL` 的
`gachaPoolDetail` 全为 `-`（1 字节），`dynMeta` 只对 `CLASSIC`/`SPECIAL`/`ATTAIN`/`BACKFLOW`/
`FESCLASSIC`/`CLASSIC_DOUBLE`/`GACHAWITHSPECIFIED6` 有值。**因此官方表不能单独产出 UP 名单。**

**对齐策略（四级，`games/arknights/data.py::align_banners`）**：

1. **开池时刻精确相等** —— 绝大多数池走这条
2. **池名归一化后相等** —— 归一指「去【】前缀、去『·复刻』后缀、去空白」。这一级不是锦上添花：
   实测有 7 个池 PRTS 写 12:00 而官方写 07:00（如 `LIMITED_79_0_1`），只能靠官方写的真名捞回
3. **结束时刻相等且开池时间差 ≤3 天**
4. **开池时间差 ≤6 小时且类别落在该分节允许的集合内** —— 同一天可能既开限定池又开回归池
   （2026-03-10 实测），靠分节收窄；仍不唯一就放弃

对不上的行进 `unmatched`，**绝不硬塞给某个池**：宁可这个池显示「UP 名单未获取」，也不能把
别的池的名单挂上去。实测当日 70 条 PRTS 记录全部对齐，0 条未对齐、0 条多义。

**分节即类别**：PRTS 的四个分节（限时寻访 / 常驻标准寻访 / 常驻中坚寻访&中坚甄选 /
新人特惠寻访）直接给出池的类别，比 `gachaRuleType` 可靠——这正是纠正 `DOUBLE`/`NORMAL`
命名反直觉问题的依据（R-12）。限时寻访一节里混着限定、联动与普通活动池，再按池型分一次。
新人特惠一节整节丢弃（`MIN_BANNERS` 之外的另一条硬规则）。

降级链：

1. PRTS 抓取成功 → 用最新骨架 + 最新名单
2. PRTS 失败 → 用内置快照的名单，池骨架仍取官方最新
3. 两源都失败 → 全量用内置快照，并在 `/卡池查询` 顶部标注「数据为 X 前的快照」
4. 名单缺失且骨架有该池 → 该池按「无 UP 加成」运行（全池均分），结果标注
   「UP 名单未获取」；**不允许**因缺名单就整池不可用

**R-15 交易与渲染顺序**：抽卡事务先提交，再渲染。渲染抛异常 → 发文字结果 + 记警告日志，
抽数与计数器保持已入账状态。

**R-16 用户隔离**：所有存档以 `(平台, 用户 id)` 为主键维度，群内互不可见；管理员操作同样写
被操作者的行，不合并。

**R-17 基础池隔离**：每个干员带一组基础池——`standard`（标准寻访 156 人）、
`classic`（中坚寻访 178 人）、`limited`（限定寻访 27 人）、`linkage`（联动寻访 19 人）。
一个干员可以同时属于多个基础池（标准与中坚重叠 62 人），四类合计可寻访 318 人。池按类别
取交集：常驻与限时取 `standard`；中坚取 `classic`；限定取 `limited + standard`；联动取
`linkage + standard`。后两类必须带上 `standard`，因为它们的低星与歪出来的六星仍来自标准池
（联动干员里没有 3★/4★，只给 `linkage` 会在抽到 3★ 时无人可抽）。`FESCLASSIC` 是限定
复刻池，按池型覆盖为 `classic + limited`。

数据的唯一来源是 PRTS 干员一览的 `data-obtain-method`，不是官方表的 `itemObtainApproach`
——后者记录的是「主要获取途径」，会把凭证交易所的 14 人、活动赠送与主线剧情干员一起当成
可寻访。凡是不属于任何基础池的干员一律不进字典（本期 103 人），因此「抽到阿米娅、暴行」
这类结果在数据层就不可能发生，而不是靠抽卡逻辑现场过滤。

**R-18 出图版式**：出图照游戏内寻访结果界面，一张 1024×576 的横屏图，单抽与十连共用同一
画布、同一张卡。

- **十连**：10 张竖卡横排，单卡 112×305，卡间距 −16（相邻卡互相压叠），整排水平居中。
  卡内自下而上为卡背 → 6★ 卡背渐变 → 网点纹理 → 半身像；星级条与职业图标是**独立层**，
  不被卡片裁切：星级条压在卡顶上方 10px，按参考实现的算法「每颗星固定 15px + 星间 2px」
  拼出总宽（6★ = 6×15 + 5×2 = 100px，素材原生 132px），职业图标 82px、底部溢出卡底 32px。
  立绘宽 = 卡宽 × 1.35（151px），**裁到卡背黑边框内侧**：卡背素材自带一圈黑边框
  （3★/4★ `back_low_1_3`/`back_four` 140×388 → 左 9 / 右 9 / 下 19；5★/6★ `back_five`
  144×392 → 左 10 / 右 12 / 下 20），立绘边界与彩条区边界重合。裁到卡边界会让立绘压住
  「卡与卡之间那条分隔黑边」，相邻两卡连成一片（2026-11-17 用户反馈）；

  6★ 卡背渐变。其余画面元素一律是游戏内 UI 贴图，不用代码画几何形状。
- **与参考实现的关系**：2026-11-17 用户要求「素材用 `gacha_primary_material`、生成参考
  `image_renderer.py`」，于是参数表与合成流程**整段照抄**（`composer_config` /
  `image_composer` 的十连与单抽 v3）。除下面一处外不改数值：同一组干员分别由两套实现渲染，
  逐像素比对仅**立绘左右各 9px 的裁切带**不同（即上面那条「不额外内缩」）。
- **素材**：UI 贴图随包（`resources/ui/`），字体随包（`resources/fonts/`）；**立绘与职业图标

  且恰好等于 `<char_id>_1`，覆盖率 100%，不需要另建映射表。PRTS 另有
  `半身像_<中文名>_1.png`（同为 180×360，人物更近、头顶留白 6~31px 更不整齐，且要中文名映射），

  600px 缩略图。PRTS 有 WAF，请求须带完整浏览器头并以 ≤1 次/秒限速；初始化起后台任务全量
  预热，抽卡时若仍缺图则当场取，取不到画占位块，**不因缺图失败**。
  半身像本人物的横向位置与胸像大小由画师决定（151 张实测脸中心横向标准差 ≈12px、头顶留白
  P90 = 15px），**程序无法可靠识别脸部**（肤色启发式在白发/深肤色/手部入镜时会误判），
  所以不做自动居中；要逐人精调只能维护锚点表，见 issue 11 的 Comments。
- **文字来源**：中文名、英文名、职业、阵营全部取自干员字典（R-17 的同一份 `characters.json`），
  渲染层不另行查网页、不做名字推断。
- **字体**：当前用 `HarmonyOS_Sans_SC_Bold.ttf`（与参考实现同款）。用户 2026-11-16 指出该字体
  与游戏内不符，**待换字体**，不作为本期验收项；字号与行距按元素表走，换字体只改字体文件与
  字号常量。

**R-19 自选池（中坚甄选 `FESCLASSIC` / 定向甄选 `SPECIAL`）**：这两类池开抽前要求玩家从
官方给的范围里自选若干干员作为本期 UP。范围、名额与份额**全部来自官方 `dynMeta`，不依赖
PRTS**——PRTS 的老池没有名单，对上的那期给的也只是「范围」而不是「UP」，当 UP 用会把概率
算错一个数量级。

| 池型 | 界面名 | 6★ 范围 | 6★ 自选 | 6★ 每人份额 | 5★ 范围 | 5★ 自选 | 5★ 每人份额 |
|---|---|---|---|---|---|---|---|
| `FESCLASSIC` | 中坚甄选 | 12 | 2 | 25% | 24 | 3 | ≈16.67% |
| `SPECIAL` | 定向甄选 | 6 | 3 | 33.33% | 6 | 3 | 20% |

- **份额的出处**：`FESCLASSIC` 官方直接给 `dynMeta.pickUpPerCharPercent`（`TIER_6`=0.25、
  `TIER_5`=0.1666625）；`SPECIAL` 没有该字段，从 `star6ChooseRule` / `star5ChooseRule` 的文案取
  （3 名合计占 6★ 的 100%、5★ 的 60%）。
- **分配方式**：选中者总份额 = 人数 × 每人份额；**剩余份额由范围内其余成员均分**；范围外的
  人在该星级**不出**。4★/3★ 不受范围限制，仍走 R-17 的通道。
  实测校正：中坚甄选改为自选后，选定者由「12 人均分（各 8.3%）」变成「各 25%」，其余 10 人
  各 5%——**此前实现把范围当 UP 且份额 1.0，目标干员概率被低估约 3 倍**；定向甄选此前没有
  名单，6★ 直接在整个标准池里均分，**范围外的 6★ 也能出**，比前者更偏。
- **范围与顺序**取 `dynMeta.rarityPickCharDict` 的 `TIER_6` / `TIER_5`，**保留官方原序**——
  序号就是按这个顺序编的，顺序一变序号就失去意义。
- **未自选不允许抽**（官方文案：「可在甄选范围内选择并锁定…选定后本次寻访不可变更」）。
  `/单抽`、`/十连` 命中自选池且无自选记录时报错并给出指令提示，**不扣抽数、不产生结果**。
- **提交即锁定**（照官方「不可变更」）：一次提交必须正好满足名额（中坚 2+3、定向 3+3），
  不足或超出整单拒绝、一个字都不写库；写库后不可修改，直到该池结束。不做「先选一部分」
  的中间态——那等于允许改动已生效的 UP。
- 自选只影响本池的星级内分配，**不影响水位、选调与契约**（这几项本来也不登记这两种池型）。
- **降级**：`dynMeta` 缺 `rarityPickCharDict` 时退回旧行为（PRTS/通道均分）且不要求自选，
  结果页标「自选范围未获取」。这是防御分支——现有 15 个 `FESCLASSIC` 与 8 个 `SPECIAL`
  全部带该字段。

**R-19b `/自选` 指令与两段式交互**：第 9 条指令，`/自选 [类别] [池名前缀] [名字或序号...]`。

- **定池**：复用 R-12 的类别 + 池名前缀，但候选只在**进行中的自选池**里挑。同时开两个自选
  池时（历史上 4 次重叠：2025-05、2025-11、2026-02、2026-05，最长 11 天）列出两个，要求带
  池名；只有一个时不要求。默认不带池名也允许「中坚」「限时」这类类别前缀。
- **候选列表**：6★ 在前、5★ 在后，**连续编号 1…n**（n = 两段之和），同一池每次编号一致。
  已选的打标，未选的留白。名字与序号可以混用——先按数字查位、再按名字查候选（复用
  `exchange.resolve` 的前缀匹配，重名多义时列候选、不替用户猜）。
- **两段式**：第一次提交只给**预览**（已选 6★ A、B / 5★ C、D、E + 「确认后本池不可变更」），
  不写库；发起人在 **5 分钟**内回复「确认」才落库，回「取消」丢弃。超时、换池、发别的指令
  都让预览失效。
- **多轮会话**：`/自选` 不带参数进入「待选」，机器人列候选后，发起人可以直接发数字
  （如 `3 7 13 14 15`）或候选名字，等价于带参数的预览；再发「确认」落库。
  实现是一条**全局消息钩子**（AstrBot 的 `RegexFilter` 不受唤醒前缀限制），因此必须严格限定：
  **只认发起人**、**只在该用户有活跃会话时**、**只认纯数字/分隔符、「确认」、「取消」，或全部
  命中本池候选的名字**；命中即 `stop_event()` + `should_call_llm(False)`，别的一条都不拦。
  会话存内存，重启即失效——不写库，避免半截状态。
- **展示三处**：`/卡池查询` 的自选池行显示「自选未选定（/自选 选人）」或
  「自选 6★ A、B · 5★ C、D、E」；`/自选` 列候选与已选；抽卡结果在标题下加一行「本池自选：…」。
- **存档**：新表 `pool_choice`，池结束后与过期水位、契约一样**惰性删除**——池 id 不复用，
  删行等价于清空。

## Technical Specification

### Data Model

**SQLite**（`data/plugin_data/astrbot_plugin_game_gacha/gacha.db`）

| 表 | 字段 | 说明 |
|---|---|---|
| `users` | PK(`uid`, `platform`), `tickets`, `created_at`, `last_signin` | 抽数余额与签到日（`YYYY-MM-DD`，本地时区）。主键带 `platform`：同一个号在 QQ 与别处是两个人（R-16） |
| `inventory` | `uid`, `platform`, `char_id`, `count`, `first_at`，PK(`uid`,`platform`,`char_id`) | `count` 为累计获得次数，潜能 = `count − 1`（展示时封顶 5，库里不封顶） |
| `pity` | `uid`, `platform`, `group_key`, `six_counter`，PK(`uid`,`platform`,`group_key`) | `six_counter` = 连续未出 6★ 次数。`group_key` 由 `pity_groups.json` 翻译（R-04）：共享组是 `standard` / `classic`，按池组是 `limited:<池id>` 这类。同一个用户会同时存在多行 |
| `pool_state` | `uid`, `platform`, `pool_id`, `pulls`, `first10_hit`，PK(`uid`,`platform`,`pool_id`) | 池内累计抽数与「前 10 抽保底是否已达成」。`first10_hit` 只进不退（写入取 `MAX`），出过一次 5★ 以上即置真 |
| `pool_select` | `uid`, `platform`, `pool_id`, `up_miss_counter`, `select150_used`, `select300_used`, `target6_locked`，PK(`uid`,`platform`,`pool_id`) | R-05 的两档「已用」标记与已锁定的那名干员（`target6_locked` 存 `char_id`，供 300 档避开同一人）；`up_miss_counter` 供 R-06（连续未出 UP 的抽数，与前者不同口径）。一行对应一个池，换期天然隔离 |
| `limited_state` | `uid`, `platform`, `pool_id`, `contracts`, `well_claimed`, `linkage_miss`, `linkage_used`, `up5_obtained` | 限定/联动专有计数。`contracts` 供 R-08，`well_claimed` 供 R-07，后三列供 R-10 |
| `pool_choice` | `uid`, `platform`, `pool_id`, `six_ids`, `five_ids`, `locked_at`，PK(`uid`,`platform`,`pool_id`) | 自选池（R-19）锁定的名单：`six_ids` / `five_ids` 为逗号分隔的 `char_id`，顺序即 `dynMeta` 原序。池结束惰性删行。与 `pool_select` 分开：那张表记的是阈值计数（会归零），这张表是一次性名单（不可改） |
| `meta` | `key`, `value` | 数据版本（官方表 ETag、PRTS 快照时间） |

`meta` 以外的每张表都带 `platform` 并进主键——R-16 对每张表都成立，只有 `users` 一行
写 `platform` 会让其余表的隔离变成靠 SQL 自觉。

**数据文件**（随包；快照在 `resources/snapshot/`，规则文件在 `resources/`）

| 文件 | 内容 | 生成方式 |
|---|---|---|
| `gacha_table.json` | 官方表裁剪：只保留池骨架需要的字段 | `tools/build_data.py` |

**新游戏能不能套进 core**（2026-11-20 脑内检验，未写代码）

四条判据，套不进去就说明接口缺东西：

| 判据 | 方舟 | 星铁 | FGO | 蔚蓝档案 |
|---|---|---|---|---|
| 星级权重 + 软保底 | 3–6，51 抽起 +2% | 3–5，74 抽起陡升 | 1–5，无软保底 | 1–3，无软保底 |
| 星级内分配（`member_weights`） | 6★ 50% / 限定 70% / 自选 100% | 50%（光锥 75%） | ★5 的 80% | 3★ 的 23% |
| 抬下限（`raise_floor`） | 每池前 10 抽必 5★+ | 每 10 抽必 4★+ | 每十连 1 张★4+ | 每十连必 2★+ |
| 跨抽次状态机 | 水位 / 联动 120 / 选调 150·300 | **50-50 歪了下次必中、定轨值** | 无 | 无 |
| 累计天井 | 300 抽送当期 | **没有**（靠 90 抽硬保底） | 330 抽 | 200 抽点数兑换 |

结论：**FGO 与蔚蓝档案能直接套**（都落在「权重 + 份额 + 阈值」三件套里，FGO 把软保底
参数置空即可）；**星铁是最难的一个**——双池类型、大小保底状态机与定轨值都不是池内
权重能表达的东西，只能作为该游戏自己的抽卡流程写在 `games/hsr/engine.py` 里。

这正是本轮只定「池骨架 + 概率件」、不定 `Game` 协议的原因：星铁的状态机会逼出接口的
真实形状，提前定就是猜。反过来，拿星铁当第一个第二游戏是有利的——它会把接口逼够宽。

### Validation Rules

- 抽数余额：单抽 ≥1、十连 ≥10，否则整单拒绝
- 池名：去首尾空白，最长 20 字；不接受纯数字
- 类别字符串只认五个词，其余当作池名前缀处理
- 改次数：绝对值 ≤ 100000，负数不得使余额为负（负数超额时按「清零」处理并回报实际改动量）
- 契约兑换：档位只认 75/200/300，目标必须在该档候选名单内
- 自选名额：必须**正好**满足（中坚 2 名 6★ + 3 名 5★，定向 3 名 6★ + 3 名 5★）；不足或超出
  整单拒绝，不写库。同一名干员不能选两次
- 自选序号：必须是 1…n 内的整数（n = 本池候选总数）；名字必须命中本池候选，多义时列候选
- 自选锁定：已有 `pool_choice` 行时任何再提交都拒绝，文案点明「已锁定，不可变更」
- 日期：签到按本地时区自然日判定，跨日以 `YYYY-MM-DD` 不等为准
- 数值落库前全部转 int，概率计算保留 double，不落库
