## Further Notes

### 待确认问题

分六组，答哪组都行，不必一次答完。答案落进上面各段后，本清单对应条目删除。

#### A. 卡池数据从哪来

1. 内置一份卡池快照随插件发布，还是运行时联网抓 PRTS？
   （抓 PRTS = 永远最新但会挂；内置快照 = 稳但要手动更新）
2. 只支持「当前进行中的卡池」，还是要能回溯复刻历史卡池？

#### B. 抽数经济

3. 抽数怎么来：每日签到 / 初始赠送若干次 / 管理员手动发 / 干脆无限抽？
4. 要不要「潜能仓库」（记录抽到过谁、重复几次）？还是抽完就丢、只回过结果？

#### C. 呈现形态

5. 结果要**图片**还是**文字**？
   - 纯文字（含 emoji 星级）：几小时能做完
   - 仿游戏截图级图片：参考实现花了 3000+ 行 + 5.4 MB 素材，是另一个量级的事

#### D. 交互入口

6. 只要 `/单抽` `/十连` 这类指令，还是要 LLM 工具（群里说「帮我抽十连」也行）？
   参考实现**只有指令**，自然语言是我们要新增的能力。

#### E. 保底水位

7. 水位（六星计数器）按池型各自独立，还是一对计数器全局共用？
   参考实现是**全局一对**，且它 JSON 里的 `counter_inherit` 字段从未被读取 ——
   官方「水位按池继承」的机制它其实没实现。我们要不要做对？

#### F. 其他

8. 星穹铁道的抽象现在就要预留吗，还是等方舟跑通再说？
9. 要不要一个「模拟 N 连看概率」的统计指令，用来验证引擎没写歪？
10. 群聊场景要不要限速（比如同一人 10 秒内只能抽一次），防刷屏？

### Input for Spec（不是最终技术契约）

这些是已经想清楚的技术倾向，`/to-spec` 时作为输入，不要在 PRD 阶段当成定论：

- 抽卡概率用「权重上限轮盘 + 溢出裁剪」模型（上限 10000，1 权重 = 0.01%），与官方公示对齐
- 池型规则外置为 JSON，不写死在代码里
- 抽卡引擎与呈现解耦：渲染失败不能让抽卡失败
- 概率引擎适合先写测试（`/tdd`）：大样本下各星级频率落在置信区间内，而不是断言抽到谁
