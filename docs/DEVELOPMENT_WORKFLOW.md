# 开发流程

本仓库怎么把「你的一句话需求」变成「能跑起来的代码」。给不写代码的人读的版本。

配套：`docs/AI_DOCUMENT_SYSTEM.md`（文档结构真相源）、`CONTEXT.md`（术语）、`AGENTS.md`（项目约定）。

---

## 一、一句话

**需求先变成纸，纸再变成代码。** 纸分成四层，每层只回答一个问题：

| 文档 | 只回答一个问题 | 位置 |
|---|---|---|
| PRD | 用户要什么？ | `docs/features/<feature>/PRD.md` |
| PLAN（可选） | 先做哪块？ | `docs/features/<feature>/PLAN.md` 或 `docs/plans/` |
| SPEC | 做成什么样才算对？ | `docs/features/<feature>/SPEC.md` |
| issue | 这一次改什么？ | `docs/features/<feature>/issues/NN-*.md` |

越往下越具体，越往上越权威。**下层不许推翻上层**：代码和 SPEC 打架时以 SPEC 为准；
SPEC 和 PRD 打架时以 PRD 为准。若上层本身错了，先改上层，再改代码 —— 不允许让既成事实
悄悄变成新规则。

## 二、流程

```text
你说需求
   ↓  /to-prd
PRD.md            产品范围、用户故事、不做什么
   ↓  /to-plan（可选）
PLAN.md           只有跨阶段/跨功能才需要
   ↓  /to-spec
SPEC.md           行为、状态、数据形态、验证命令
   ↓  /to-issues
issues/01..NN     一条一个垂直切片
   ↓  逐条实现 + /tdd（该写测试的部分）
代码 + 提交
   ↓
你验收 → 不满意回顶部改 PRD 或 SPEC
```

### 阶段一：说需求 → PRD

- **你说**：谁用、什么场景、看到什么、什么算不对。口语即可，不用管格式。
- **我做**：`/to-prd` 写成 `PRD.md`，只记产品层的东西 —— **不写 API、不写表结构、不写文件路径**。
- **判据**：读完 PRD 你能指出「这条不是我想要的」。指不出来说明写得太技术了。

PRD 写不出来的情况只有一种：需求本身有缺口。这时我把缺口列成问题问你，不猜。

### 阶段二：要不要 PLAN

- **跳过**（大多数情况）：一个 SPEC + 3~5 条 issue 就够了。
- **要写**：功能跨多个阶段、跨多个功能、或属于一次版本发布，需要先定先后顺序和风险。
- **判据**：PLAN 只排先后，不定义契约、不拆任务。它要是开始写「接口长什么样」，就写错层了。

### 阶段三：SPEC

- **我做**：`/to-spec` 把 PRD 翻成行为契约——每个用户可见行为对应一条规则或场景，
  外加错误场景、数据形态，以及**能直接执行的验证命令**。
- **判据**：SPEC 里每条规则都能追溯到 PRD 的某条用户故事。发明 PRD 里没有的范围 = 写错。
- **不做的**：不写「先建 X 模块再写 Y 函数」这种实施步骤，那是 issue 的事。

### 阶段四：拆 issue

- **我做**：`/to-issues` 按 **垂直切片** 拆 —— 每条都窄，但端到端打通（能单独跑、单独验、单独回滚）。
  不是「先写完所有数据层，再写所有指令层」。
- **你审**：粒度是否合适、依赖顺序对不对、哪些需要你先拍板（HITL）、哪些我能自己做（AFK）。
- **判据**：一条 issue 应当能独立验收。做不到就继续拆。

### 阶段五：实现与验收

- 一条 issue 一次提交，中文约定式前缀，正文列改了哪些文件。
- 涉及概率、边界、解析这类算得清的部分，先写测试（`/tdd`）。
- **验收由你来**：我把可执行命令和预期行为写在 issue 的 `Verification` 里，你在群里实际试一遍。

### 出问题：`/diagnose`

行为不对、报错、结果离谱 → 先复现再定位，定位到具体模块再改。
不允许「顺手改改看能不能好」——那会把问题变成谜。

## 三、issue 的状态机

```text
needs-triage ──→ needs-info（等我问清楚）
     │
     ├──→ ready-for-agent   四个条件齐：AFK / 验收标准完整 / 有可执行命令 / 无待确认问题
     ├──→ ready-for-human   需要你拍板或需要人做
     └──→ wontfix           不做
```

状态写在 issue 文件顶部的 `> Status:` 行。`ready-for-agent` 不是荣誉称号，
缺一条就得降级 —— 具体四条件见 `docs/agents/triage-labels.md`。

## 四、你常说的三种话，对应三种动作

| 你说 | 我做什么 |
|---|---|
| 「再加个功能」 | 先改 PRD（用户故事 + 范围），再走 SPEC、拆 issue |
| 「这个行为不对」 | 先判断是 SPEC 写错了还是代码写错了；SPEC 错就改 SPEC，再改代码 |
| 「崩了 / 报错」 | `/diagnose`：复现 → 定位 → 改 → 加一条防回归的验证 |
| 「这个词到底啥意思」 | `/grill-with-docs`：逼问清楚后写进 `CONTEXT.md` |

## 五、硬规则

1. **遇到分叉先问我**，两条路都说得通时不替你选。
2. **一个模块一次提交**，中文提交信息。
3. **只改本仓库与 `data/plugin_data/astrbot_plugin_game_gacha/`**，AstrBot 源码与配置不碰。
4. **术语照 `CONTEXT.md`**：说「水位」不写「保底计数器」，说「抽数」不写「余额」。
5. **文档先行**：SPEC 里没有的行为不做，哪怕它看起来很明显。
6. **不藏未知**：不确定的东西写进 `Open Questions`，不在代码里偷偷定。

## 六、常见误区

| 误区 | 为什么错 |
|---|---|
| PRD 里写数据库表结构 | 表结构会变，PRD 应该是稳定的产品意图 |
| SPEC 里写「先建 X 文件再建 Y 文件」 | 那是实施步骤，会随代码过时；契约不会 |
| 一条 issue 写「实现抽卡功能」 | 太大，验收不了，回滚不了 |
| 代码先写，文档事后补 | 补出来的文档是代码的解释，不是需求的来源 |
| issue 里 Automated Checks 留占位符 | 那就不能标 `ready-for-agent` |
