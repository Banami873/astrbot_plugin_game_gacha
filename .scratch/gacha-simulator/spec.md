## 实现决策

已定：
- 抽卡概率用「权重上限轮盘 + 溢出裁剪」模型（权重上限 10000，1 权重 = 0.01%），
  与官方公示概率对齐。详见参考拆解第二节
- 池型规则外置为 JSON，不写死在代码里
- 抽卡逻辑（引擎）与呈现（文字/图片）解耦：渲染失败不能让抽卡失败
- 数据落 `data/plugin_data/astrbot_plugin_game_gacha/`，不写插件安装目录

〔待定〕模块划分、存储结构、卡池数据契约、是否需要 LLM 工具。

## 测试决策

〔待定〕倾向：概率引擎用统计测试（大样本下各星级实际频率落在置信区间内），

## 补充说明：待你回答的问题

分六组，答哪组都行，不必一次答完。答完我填上面各段。

### A. 卡池数据从哪来

1. 内置一份卡池快照随插件发布，还是要运行时联网抓 PRTS？
   （抓 PRTS = 永远最新但会挂；内置快照 = 稳但要手动更新）
2. 只支持「当前进行中的卡池」，还是要能回溯复刻历史卡池？

### B. 抽卡次数（经济系统）

3. 次数怎么来：每日签到 / 初始赠送若干次 / 管理员手动发 / 干脆无限抽？
4. 要不要「潜能仓库」（记录抽到过谁、重复几次）？还是抽完就丢、只回过结果？

### C. 呈现形态

5. 结果要**图片**还是**文字**？
   - 纯文字（含 emoji 星级）：几小时能做完
   - 仿游戏截图级图片：参考实现花了 3000+ 行 + 5.4 MB 素材，是另一个量级的事

### D. 交互入口

6. 只要 `/单抽` `/十连` 这类指令，还是要 LLM 工具（群里说「帮我抽十连」也行）？
   参考实现**只有指令**，自然语言是我们要新增的能力。

### E. 保底水位

7. 水位（六星计数器）按池型各自独立，还是一对计数器全局共用？
   参考实现是**全局一对**，且它 JSON 里的 `counter_inherit` 字段从未被读取 ——
   也就是说官方「水位按池继承」的机制它其实没实现。我们要不要做对？
